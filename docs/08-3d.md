# 08 3D houses (PlanTo3D)

A floor plan PDF becomes a furnished house the user walks through in the browser. The 3D is built by **PlanTo3D**, a separate service with no AI model: its detector is geometry, its furniture is rules, and the house is built and lit in Blender.

```
Browser (our pages + PlanTo3D's pages in iframes)
   |  Bearer token for our API          |  signed token in the URL for iframes and files
   v                                    v
FastAPI gateway  /api/v1/3d  ---------> PlanTo3D  http://127.0.0.1:8080  (private, no login)
   |                                       |
   plan3d_jobs (who owns which job)        jobs/<id>/ (plan.json, house.glb, light maps, ...)
```

## Readers: no upload ends on an error

Every PDF reaches the review page. The readers are tried in this order, and the job says which one made the plan
(`reader`) and what to check (`notice`); the review step shows both.

| Reader | When | Notes |
|---|---|---|
| `detector` | Always first: PlanTo3D's own detector starts on upload. | CAD vector drawings, including walls drawn as solid bands (our generator's style), forms and clip paths, metric and area labels. |
| `ai` | The detector refused or failed (a scan, a photo, an unknown style). | Our AI plan parser (`parsing.service.read_plan_with_ai`, a model call unless cached) gives PlanJSON 2.0; `convert.py` turns it into PlanTo3D's plan JSON and the gateway imports it. While it runs (about a minute) the job reads `detecting`. |
| `trace` | The AI reader failed too, or its plan looks implausible (`convert.check_plausible`). | The review page opens on the page image with whatever geometry there is; the person traces the walls (Draw wall, Add door / window / stairs) and sets the scale from two points. |
| `stored` | A PDF exported by our floor plan generator, uploaded by that plan's owner, or "Open in 3D" in the generator. | No reading at all: the stored plan is converted and imported. The generator's PDF carries `constriva-plan:<id>;v=<version>` in its Keywords (`render/exports.py`); the gateway uses it only after checking the plan is the user's. |

A plan that is not in the PDF's own coordinates (ai, stored, trace) is laid over the page image by the review page's
own fit; "Line up drawing" matches two points. A sideways sheet is read as it lies (the house comes out a quarter
turn round and a sideways title is not found).

## Rules

1. **PlanTo3D is private.** It has no login, so it listens on 127.0.0.1 only, with no CORS (`scripts/run_planto3d.sh` refuses `--host` and `--cors`). A browser never calls it.
2. **Everything goes through the gateway.** `/api/v1/3d` signs the user in (the app's one auth dependency), checks the job is theirs in `plan3d_jobs`, and forwards the request. Someone else's job is a 404.
3. **Iframes and downloads use a signed token.** A browser cannot send the Bearer token for an `<iframe>` or a file link. `POST /api/v1/3d/jobs/{id}/embed` returns URLs under `/api/v1/3d/embed/<token>/...`. The token names one user and one job, expires (`PLAN3D_EMBED_TOKEN_TTL_S`, default one hour), and forwards only what PlanTo3D's pages need: its pages, three.js, that job's files and status, saving the reviewed plan, the Blender export, converting a recording, and the furniture models. It never lists jobs, uploads, builds or deletes. Responses carry `frame-ancestors` for our frontend only and `Referrer-Policy: no-referrer`. A token is part of the URL, so it appears in the API's access log: keep its lifetime short.
4. **Plan uploads are checked once, the same way everywhere:** PDF only, size and page limits (`parsing.service.read_plan_upload`), before PlanTo3D sees the file.
5. **No AI in PlanTo3D.** Scans and photos are refused by its detector.

## Qualities

| In our pages | PlanTo3D | What it is |
|---|---|---|
| Low | `draft` | The fast build: light maps up to 2048 px, baked with 64 samples |
| Medium | `high` | Light maps up to 4096 px, baked with 256 samples. About ten times slower than Low |
| High | (none) | Cinema video tour. PlanTo3D renders it with a command-line tool (`blender/cinema.py`) that needs a camera route written by hand, and its server has no API for it. The gateway names it, marks it `coming_soon` (the pages show "Coming soon") and answers `501` until it is built with the Ultra tier. |

## Gateway API (`/api/v1/3d`)

| Method and path | Purpose |
|---|---|
| `GET /system` | Is the builder reachable and set up (Blender, PDF tools, viewer library, materials), and which qualities can be built. |
| `POST /jobs` | Multipart `file` (PDF) and optional `project_id`. Starts detection. `201 {job_id}`. |
| `POST /jobs/sample` | The same with PlanTo3D's sample plan. |
| `POST /jobs/from-floorplan` | `{plan_id}`: a plan of our floor plan generator, opened without reading any drawing (`404` unless it is the user's). |
| `GET /jobs` | The user's jobs (optional `?project_id=`). |
| `GET /jobs/{id}` | `stage`, `progress`, `message`, `eta_left`, `queue_position`, `quality`, `build_seconds`, `reader` (`detector`, `ai`, `stored`, `trace`) and `notice`. Stages: `uploaded`, `detecting`, `detected`, `queued`, `building`, `done`, `failed`. |
| `POST /jobs/{id}/build` | `{quality: low | medium | high}`. |
| `POST /jobs/{id}/export` | Packs the Blender file. `{file}` to download under the embed `files_url`. |
| `POST /jobs/{id}/embed` | Signed URLs for the review, walkthrough and furniture pages and the job's files. |
| `POST /embed` | The furniture models page alone. |
| `DELETE /jobs/{id}` | `409` while it is being built. |
| `GET, POST, DELETE /embed/{token}/{path}` | PlanTo3D's pages and files for an iframe. Not in the OpenAPI document. |

The review page runs in an embed mode: it has no build button. Our page posts `{source: 'planto3d-host', type: 'save', furnish}` to it, waits for `{source: 'planto3d', type: 'saved'}`, then calls `POST /jobs/{id}/build`. See `PATCHES.md`.

## Settings

| Variable | Default | Meaning |
|---|---|---|
| `PLAN3D_SERVICE_URL` | `http://127.0.0.1:8080` | Where PlanTo3D listens. |
| `PLAN3D_EMBED_SECRET` | random per process | Signs embed tokens. Set it in production: without it tokens stop working at a restart and with more than one API worker. |
| `PLAN3D_EMBED_TOKEN_TTL_S` | `3600` | Lifetime of an embed token. |
| `PLAN3D_STORE` | `supabase` | `memory` keeps job ownership in the API process (lost at restart), for local work before the table exists. |
| `PLAN3D_TIMEOUT_S` | `30` | Timeout of a call to the service. |
| `PLAN3D_ALLOW_FURNITURE_CHANGES` | `true` | Let signed-in users replace furniture models. PlanTo3D keeps one set of models for everybody. |
| `PLAN3D_FRAME_ANCESTORS` | empty | Extra origins allowed to frame the pages. `FRONTEND_ORIGIN` is always allowed. |

## Database

`plan3d_jobs` maps a PlanTo3D job id to its owner and project. It is not applied automatically. Either run, with `DATABASE_URL` pointing at the database:

    uv --directory backend run alembic upgrade head

or paste this into the Supabase SQL editor:

```sql
create table plan3d_jobs (
  id          text primary key check (id ~ '^[a-f0-9]{12}$'),
  user_id     uuid not null,
  project_id  uuid references projects(id) on delete set null,
  name        text not null default '',
  source      text not null default 'upload' check (source in ('upload', 'sample')),
  quality     text check (quality is null or quality in ('low', 'medium', 'high')),
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
create index plan3d_jobs_user_created on plan3d_jobs (user_id, created_at);
create index plan3d_jobs_project on plan3d_jobs (project_id);
alter table plan3d_jobs enable row level security;
create policy plan3d_jobs_owner_read on plan3d_jobs for select using (auth.uid() = user_id);
```

`user_id` has no foreign key: the table that holds users was not inspected when this was written. Add one if it suits the schema.

## Setup and running

    scripts/setup_planto3d.sh          # Blender, poppler, Node, ffmpeg, three.js, CC0 materials (about 75 MB)
    scripts/setup_planto3d.sh --check  # only report
    scripts/run_planto3d.sh            # http://127.0.0.1:8080

`GET /health/deep` on the API includes a `planto3d` check, which is PlanTo3D's own `GET /api/system`. `GET /api/v1/3d/system` gives the same to the upload page.

Never commit `services/planto3d/assets/`, `services/planto3d/jobs/`, client drawings or `docs/reference/`: they are in `.gitignore`.

## What replaced what

The earlier 3D viewer built meshes in the browser from PlanJSON. It, and the import flow that fed it, were removed: `frontend/src/viewer3d`, `frontend/src/features/plan-viewer`, `features/plan-editor`, `features/files/ImportPlanPage.tsx`, the endpoints `/api/v1/parsing/process`, `/parsing/stream/{id}`, `/parsing/job/{id}/image`, `/parsing/{project_id}/plan`, `/api/v1/plans/{id}`, `/plans/project/{id}`, `PUT /plans/{id}`, `ParsingService`, and the `parse_plan` worker task. The plan parser, PlanJSON and the BOQ are unchanged.
